# 전체 화면 색 격자(Screen Grid) 전송 설계

## 의도 / 이유
QR 애니메이션은 장당 약 0.4 KB라 큰 파일은 전송이 너무 오래 걸린다. 브라우저 화면 전체를 색 칸 격자로 채워 장당 수 KB~수십 KB를 보내고, ←/→ 키로 장을 넘긴다. 화면을 가려도 되는 "빈 브라우저" 상황을 전제로 한다. (사용자 결정)

## 목표
- 파일 하나를 여러 장의 격자 화면으로 보내고, 폰으로 찍은 사진에서 원본 파일을 복원한다 (끝까지 동작).
- 칸 크기·색 단계를 바꿔 가며 폰이 읽을 수 있는 한계를 실측한다 (오류율 리포트).
- 창 크기·브라우저 확대가 바뀌어도 동작한다.

## 비목표
- 폰에서의 실시간 해독, 자동 재생(영상). 이번 범위는 수동 넘김 + 사진.
- 사람 눈에 안 띄게 이미지에 심는 방식(별개 프로젝트 B).
- 반투명 오버레이로 다른 작업 화면 위에 덧씌우기.

## 사용자가 정한 것
- 브라우저 전체 영역을 색 칸으로 채운다. 불투명, 컬러 사용.
- 설정 UI는 **위쪽 가로 얇은 줄**에 둔다. 칸 크기(px)와 색 단계를 설정.
- ←/→ 커서키로 장을 넘긴다.
- **칸 크기는 실제 기기 픽셀 기준 정수로 고정**하고, 창 크기에 따라 가로·세로 칸 수가 바뀐다. 각 장에 칸 수를 심어 수신 쪽이 알 필요 없게 한다.
- 창 크기/확대가 바뀌면 현재 **바이트 위치**를 유지한 채 다시 배치한다 (처음부터 다시 보내지 않음).
- 실제 파일을 보낸다 (무작위 데이터는 테스트용 보조).
- 채널당 색 단계(2/4/8)는 설정값. 기준 색 칸으로 보정한다.

## 설계 (제 판단 포함, [판단] 표시)
**송신 `grid.html`** (정적 페이지, 서버 불필요. `server.py`에 `/grid.html` 경로도 추가) [판단]
- 위쪽 줄: 파일 선택, 칸 크기(2/3/4/6/8 px), 색 단계(2/4/8), 장 번호 ◀ ▶, 장당·전체 용량, S 키로 UI 숨김 [판단].
- 데이터 영역은 위쪽 줄 아래 나머지 전체. `canvas`를 `devicePixelRatio`에 맞춰 기기 픽셀 크기로 만들고 보간을 끈다.
- 한 칸 = (R,G,B) 각 L단계 → 칸당 3·log2(L) 비트 (L=2:3, 4:6, 8:9).
- 예약 영역: 네 모서리 위치 표식(흑/백 패턴), 맨 윗줄 기준 색 칸(흑·백·채널별 단계 램프), 헤더(칸 수, L, 장 번호/총 장 수, 파일 ID, 장 페이로드 길이, CRC). 헤더는 항상 L=2로 그려 견고하게 [판단].
- 페이로드: 파일 이름·크기 + 바이트. 장 단위 Reed-Solomon 오류 정정, 비율 기본 20%·설정 가능 [판단].

**수신 (이번 범위): `tools/grid_decode.py`** [판단]
- 장마다 찍은 사진(순서 무관, 중복 허용)을 입력. OpenCV로 모서리 표식을 찾아 원근 보정 → 기준 색으로 보정 → 칸 색 판독 → RS 복구 → 파일 복원.
- 출력: 장별 칸 오류율, RS 정정 수, 복원 성공 여부, 누락 장 목록. 의존성 추가: `reedsolo`.
- 사진 촬영 방식: 장마다 정지 사진 [판단] (수동 넘김이므로).

## 빌더 재량
칸 모양/표식 세부, 헤더 비트 배치, RS 블록 크기, 색 판독 알고리즘(보정 방식), 코드 파일 분리.

## 성공 기준
1. 1~수 MB 파일을 송신 → 장마다 사진 → 복원했을 때 바이트 일치.
2. 칸 크기×색 단계 조합별 오류율을 표로 얻는다 (폰에서 실제로 읽히는 한계 확인).
3. 창 크기/확대 변경 후에도 같은 파일을 이어서 보낼 수 있다.

## 위험
- 칸이 카메라 화면에서 3px 미만이면 읽기 어렵고, 모아레와 자동 노출이 변수다.
- 4·8단계 색은 카메라/압축 영향으로 오류가 많을 수 있다 (실측이 목적).
